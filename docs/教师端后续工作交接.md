|顺序|负责人|要做什么|完成标准|

|1|成员1牵头，成员2/3配合|审查本轮迁移、公共认证、错误结构及接口变更；在集成分支处理冲突。|三方使用同一数据库迁移头；旧客户端不再漏传版本字段；内部调用携带独立凭证。|
|2|成员2|接入真实上传、材料校验、私有访问及学生提交评审。|真实学生能提交作业，校验结果关联正确提交；评审记录有分项和提交时间；越权访问被拒绝。|
|3|成员3|把聚合、异常、运行状态落库，并实现失败重试与作业状态推进。|每条聚合关联正确作业/Panel及成功运行；重复执行不产生错误结果；可进入教师评分阶段。|
|4|成员1与成员2/3|完成跨角色联合验收。|从学生真实上传到五人互评、真实聚合、教师锁分、异常复核、最终发布和学生查分全程走通。|
|5|部署负责人，成员1验收|在隔离预发布环境运行容器、迁移和网关，演练备份恢复。|HTTPS可访问，数据库不公开暴露，密钥正确注入，重启数据不丢失，备份实际可恢复。|

成员3接入时特别注意：

* 修改同一作业的业务输入时，先锁 `assignments` 父记录，再锁子记录；参考
  `backend/app/services/teacher_workflow.py` 的 `lock_assignment`，避免与教师发布采用相反锁顺序。
* 发布要求作业处于 `TEACHER_GRADING`，至少一条有效提交，各提交材料有效、五条任务全部
  `SUBMITTED`、最新教师评分已锁定、无未处理异常。
* 聚合必须关联当前作业的正确Panel及 `COMPLETED` 运行，分值在Rubric范围内，生成时间不能
  早于最近评审提交时间。重算应保存可追溯的运行与结果，不能伪造时间满足检查。
* 已发布作业的评分输入与最终成绩被冻结；后台任务也受数据库约束，不得禁用触发器绕过。
* 算法无权修改教师分。教师分必须独立录入，AI建议不得自动成为教师评分。

## 3. 升级与运行交接

1. 获取 `teacher` 最新提交并检查工作区，再阅读接口差异和迁移。不要覆盖其他成员尚未提交的改动。
2. 备份目标数据库；先在其隔离副本上验证迁移。新迁移为 `20260930_0003`，包含数据库触发器、
   登录限流表和最终成绩权重快照。不得只更新前端而漏掉迁移。
3. 在已安装后端依赖、`DATABASE_URL` 指向正确目标的环境中，进入 `backend` 执行
   `alembic upgrade head`，再执行 `alembic current` 确认版本。
4. 同步部署前后端：评分更正传 `expected_version`；草稿编辑传 `expected_updated_at`；
   内部服务使用 `X-Internal-Token`，不能拿教师JWT替代。
5. 生产设置 `APP_ENV=production`，使用独立随机的 `JWT_SECRET` 和 `INTERNAL_API_TOKEN`
   （各至少32字符），并配置真实数据库凭证、前端HTTPS来源及必要的AI配置。
   密钥留在环境配置或密钥管理服务，不能提交仓库。
6. 独立后端容器入口为 `docker compose -f docker-compose.production.yml up -d --build`。
   新环境会使用该配置自己的数据库卷；已有环境先确认连接和卷映射，避免误连空库。
   前端执行 `npm ci`、`npm run build`，将 `frontend/dist` 交由HTTPS网关提供，并转发 `/api`。
7. 检查健康接口、真实账号登录、教师页面、学生权限和已发布成绩一致性。
   生产不能运行演示种子。若升级失败，应保留诊断信息并按已演练的备份恢复方案处理；
   不把删除卷或随意降级作为默认回滚手段。

历史权重回填来自迁移时作业配置。若旧系统曾直接修改过已发布作业的权重，必须在升级前
根据历史记录核对；迁移无法恢复从未保存的旧权重。
